An agent, a model, and an experiment to find out whether explaining a prediction makes it better.

The problem

Anyone can predict games badly.
Knowing you did it well is the hard part.

Hold out a season and test on it — routine for a classical model.

But a language model has read the internet. Ask it who won a game in December 2025 and it may simply know.

An accuracy number produced that way measures memory, not prediction — and it looks excellent, which is what makes it dangerous. The system passes the demo and is measuring nothing.

Why two gates

They are not redundant

A snapshot can only be as strict as its loosest legitimate reader.

rolling form

needs games strictly before D

schedule context

needs games through D

One on-disk cut cannot serve both without starving one. The snapshot removes what nobody may see; the filter decides what each tool may see.

And rest is not a leak. The NBA publishes its schedule in August, so back-to-backs are knowable on any date. Only outcomes are gated.

No database. No web. No way to invent a number. The two unbuilt tools report their own gap rather than guessing.

Skills

The rules live in Markdown,
not buried in Python

Each tool has a skill file — when to call it, how to read the answer. Loaded into the system prompt at startup, so a teammate changes agent behaviour without touching code.

Do not apply your own injury penalty on top of the model's number. — skills/retrieve_injuries.md

Why not a database? We considered dumping everything into Postgres and letting the agent query freely. Rejected for the same reason we removed the betting line: a free-form query surface is how an agent reaches data nobody intended it to see — and the gate only holds because every read passes through one module.

The trap we had to avoid

The obvious way to build a feature
is the leaking way

Season win percentage: group the season, take the mean.

That silently includes the game you are predicting. The result is a very accurate and completely worthless model.

Every accumulator is advanced after emitting the row. And we split by season, not random shuffle — a shuffle lets the model learn from March to predict January.

Tests that cannot fail prove nothing, so we broke each rule on purpose:

The incident

The agent cheated —
and it wasn't even trying to

It had a betting-line tool. The docstring said, in capitals, that the line was context only. Running live on 2026-01-14 it wrote this into its own reasoning:

The closing betting line favors the home team, ORL (-5.5 spread) — the agent, quoting the exact benchmark we grade it against

Nothing was violated dramatically. It was asked what drove its reasoning and truthfully reported a factor. The tool simply made the shortcut available.

Telling a model not to peek is a request. Removing the tool is a guarantee.

Result

Our hypothesis was wrong

Train 66.8% vs test 66.5% — a +0.3% generalisation gap. Not overfit.

But arm C did not beat arm A. It lost. Headline accuracy on 40 games is noisy, so the robust measure is paired:

When the agent overruled the model, it was wrong 15 times out of 19. two 40-game samples pooled · two-sided sign test p ≈ 0.019
So we fixed it

Written rules recovered
half the loss

Each tool got explicit rules — including "do not re-price injuries on top of the model". Re-ran on the same games, changing nothing but the prompt:

arm C accuracy58.8%66.3%
log loss0.6740.591

Replicates on both seeds, by the mechanism predicted: it overrules less.

Honest caveat: the override test is now under-powered (p ≈ 0.23), not passed. Less overruling to measure ≠ solved.

The measurement that changed our design

We tried to write
"star out → drop N%"

There is no N this data supports — and how that failed is the point.

ComparisonResult
All games, either star outhome wins less when the away star sitsbackwards
Only teams that have a star+5.6% more wins without him (z = 2.6)backwards, significant
Each team vs itself+0.0% (se 3.3%, n = 21)the real answer

The first two are confounded identically: having a 20-ppg scorer is a property of good teams, and a good team is still good on the night its star sits.

So the rule says the opposite of what we set out to write: report the injury, let the model price it.

Honest accounting

What we did not do

  • predict_stat_line was never built — a stated deliverable. The tool reports its own gap.
  • n = 80 across two samples for the LLM arms. Better than 40, still small.
  • Injury records are transaction dates, not news timestamps — a same-day placement can appear.
  • Star-to-team mapping is a season stale, so "injured" and "changed teams" are not cleanly separated.
  • Two data sources have no recorded upstream — including the odds file the whole benchmark rests on.
  • No opponent-adjusted strength of schedule — probably the largest gain still available.
What it adds up to

Three things worth keeping

A reusable pattern

Two-layer gate + cutoff-pinned model, for evaluating any LLM system on historical data

A small-sample method

Paired override analysis pulls signal from samples far too small for headline comparison

A concrete failure

An agent optimising into the answer key — fixed by removing capability, not adding instruction

The scope of our claim is narrow: this agent, with these seven tools, on these 80 paired games, degraded a good estimate. We have not shown that LLM agents cannot help.

A confirmed hypothesis would have told us the architecture was fine. This told us where it breaks.
